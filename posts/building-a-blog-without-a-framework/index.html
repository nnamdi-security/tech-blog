How I Built This Blog Without a Framework

A behind-the-scenes look at how this blog runs on plain HTML, CSS, and JavaScript, with no framework, no build step, and no package manager.

Nnamdi Ileh3 November 20269 min read
  • HTML
  • JavaScript
  • Netlify
  • Case Study

When I started this blog as part of my fullstack training, the obvious move was to pick a framework: Next.js, Astro, Gatsby, or a static site generator like Hugo. I went the other way. Every page on this site is a hand-written HTML file, styled with plain CSS and given a little behaviour with vanilla JavaScript. There is no package.json, no node_modules folder, and no build step. Netlify serves the files exactly as they are in the repository.

This article explains how the pieces fit together, why I made each choice, and where the approach has already caused me problems.

Why no framework?

Three reasons:

  • Learning. Frameworks hide a lot of decisions. Building without one made me learn how routing, shared layouts, SEO metadata, and forms actually work on the web.
  • Longevity. A folder of HTML files will still open in a browser in ten years. There are no dependencies to update and no build tool that can break.
  • Speed. The browser downloads finished HTML, so there is nothing to hydrate or render on the client before the article appears.

The trade-off is that I have to solve some problems myself that a framework would normally solve for me. The rest of this article covers how I did that.

Routing is just folders

The site has no router. Each URL maps directly to a folder with an index.html inside it:

tech-blog/
├── index.html                      → /
├── about/index.html                → /about/
├── posts/index.html                → /posts/
└── posts/javascript-variables/
    └── index.html                  → /posts/javascript-variables/

Web servers return index.html automatically when someone requests a folder, so these clean URLs come for free. In netlify.toml I also turn on Netlify's pretty_urls option, which keeps URLs consistent without the .html extension.

Two sources of content

This is the most important design decision on the site. Every post exists in two places:

  1. A real HTML page containing the full article, its <title>, meta description, Open Graph tags, and JSON-LD structured data.
  2. A small metadata object in assets/js/posts.js describing the post for listing pages.
export const posts = [
    {
        id: "javascript-array-methods",
        title: "JavaScript Array Methods Explained",
        type: "tutorial",
        excerpt: "A practical, beginner-friendly walkthrough...",
        publishedAt: "2026-07-16",
        thumbnail: "/assets/images/posts/javascript-array-methods.svg",
        url: "/posts/javascript-array-methods/",
        featured: true,
        tags: ["JavaScript", "Frontend", "Tutorial"]
    }
    // ...one object per post
];

The homepage, the archive, the related-posts section, the post counts, and the "older post / newer post" links are all generated from this array. To publish a post, I add one object, and every listing updates.

Why not generate the whole page from JavaScript? Because search engines and social media crawlers should never have to run JavaScript to read an article. When someone shares a post on LinkedIn, LinkedIn's crawler reads the Open Graph tags straight from the HTML. Keeping the important content in the HTML file means it is always readable, even with JavaScript turned off.

Shared header and footer with fetch()

Without a templating system, the obvious way to share a header between pages is to copy and paste it into every file. That works until you want to add a menu link and have to edit every page by hand.

Instead, each page contains an empty placeholder:

<div data-component="/components/header.html"></div>

A small script, components.js, finds every placeholder, downloads the partial, and inserts it:

async function loadComponent(element) {
    const componentUrl = element.dataset.component;

    try {
        const response = await fetch(componentUrl);

        if (!response.ok) {
            throw new Error(`Request failed with status ${response.status}`);
        }

        element.innerHTML = await response.text();
    } catch (error) {
        console.error(`Could not load shared component: ${componentUrl}`, error);
        element.innerHTML = `<div class="component-error" role="alert">...</div>`;
    }
}

async function loadAllComponents() {
    const elements = [...document.querySelectorAll("[data-component]")];
    await Promise.all(elements.map(loadComponent));
    document.dispatchEvent(new CustomEvent("components:loaded"));
}

Two details matter here. First, the paths are root-relative (they start with /), so /components/header.html resolves to the same file whether the page is at / or three folders deep. Second, once every component has loaded, the script fires a custom components:loaded event. The navigation script waits for that event before wiring up the mobile menu, because the menu button does not exist until the header has been inserted.

For visitors without JavaScript, each header placeholder also contains a <noscript> block with plain navigation links, so nobody gets stuck on a page with no way out.

SEO without a plugin

Frameworks often come with an SEO plugin. Here, every page writes its own metadata by hand:

  • A unique <title> and meta description
  • A canonical URL
  • Open Graph and Twitter/X tags for social previews
  • JSON-LD structured data describing the page as an Article, VideoObject, or PodcastEpisode, plus a breadcrumb trail

The site also has a hand-maintained sitemap.xml, feed.xml RSS feed, robots.txt, and site.webmanifest. It is more typing than installing a plugin, but I understand every line, and I know exactly what a crawler sees.

A contact form with no backend

The contact form needed somewhere to send submissions, and I did not want to run a server. Netlify Forms solves this. Netlify scans the HTML at deploy time, finds any form marked with data-netlify="true", and collects its submissions for me:

<form name="contact" method="POST" action="/success/"
      data-netlify="true" netlify-honeypot="bot-field">
    <p hidden>
        <label>Do not fill this out: <input name="bot-field"></label>
    </p>
    <!-- name, email, and message fields -->
</form>

The hidden bot-field is a honeypot. People never see it, but spam bots that fill in every field will, and Netlify quietly discards those submissions.

Deployment: one config file

The whole deployment setup is netlify.toml. It tells Netlify to publish the repository root as-is, and it sets HTTP headers. Assets in /assets/ are cached for a year, while HTML pages are always revalidated, so new posts appear straight away. Every push to main on GitHub triggers a new deploy.

What has gone wrong

The biggest weakness of this architecture is duplication. A post's slug, title, and thumbnail live in the HTML page, in posts.js, in the sitemap, and in the RSS feed. Nothing checks that they agree, and I have already been caught out twice:

  • A broken link. My variables tutorial lived in a folder called variable-explained, but its entry in posts.js pointed to /posts/javascript-variables/. Every card and "next post" link sent readers to a 404 page until I renamed the folder to match.
  • A missing thumbnail. The same post's metadata pointed to a .webp thumbnail, but the file I had actually added was a .png. The card on the homepage showed a broken image.

A framework or a build step would catch mistakes like these automatically. Without one, I rely on a checklist, careful testing, and clicking every new link before I push.

Other trade-offs to know about

  • Opening a page straight from your file system (file://) breaks the shared header, because browsers block fetch() there. You need a local server, such as python -m http.server.
  • The header appears a moment after the page, because it is fetched separately.
  • Every page repeats the same <head> boilerplate.
  • There is no Markdown. Every post is written directly in HTML.

Would I do it again?

For a learning project, absolutely. I now understand what frameworks do for me, which makes me a better judge of when to reach for one. If this blog grows to dozens of posts, the duplication will become painful, and I will probably add a small static site generator that builds posts.js, the sitemap, and the feed from a single source. Until then, plain HTML, CSS, and JavaScript are doing the job.
