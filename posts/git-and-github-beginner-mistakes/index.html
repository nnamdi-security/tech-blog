Git and GitHub for Beginners: The Mistakes I Made So You Don't Have To

Unrelated histories, surprise merge commits, and a broken URL. These are real lessons from this blog's own commit history, and how to avoid each one.

Nnamdi Ileh3 November 20269 min read
  • Git
  • Career
  • Beginners

Git keeps a permanent record of everything you do, including your mistakes. Running git log --graph on this blog's repository shows a short history of me learning Git in public: an odd merge on day one, merge commits I never meant to create, and a bug fix that turned out to be a renamed folder.

Here is what happened each time, why it happened, and what I do differently now.

Mistake 1: Starting the same project in two places

The first three commits in this repository look like this:

*   5bf3c1d Merge unrelated histories
|\
| * dc236c1 Initialize README with project title
* f1e9e3e Build initial static technology blog

I built the first version of the site on my computer and ran git init there. Separately, I created the repository on GitHub and ticked the box to add a README. That gave me two repositories with no commits in common: one with my code, one with a README.

When I tried to pull from GitHub, Git refused:

fatal: refusing to merge unrelated histories

Git was not broken. It was warning me that the two histories had nothing to do with each other, which is usually a sign that something is wrong. I fixed it by telling Git that I really did want to join them:

git pull origin main --allow-unrelated-histories

How to avoid it

Pick one place to start the project, and only one:

  • Starting on GitHub? Create the repository, then git clone it and build inside that folder.
  • Starting locally? Create an empty repository on GitHub, with no README, licence, or .gitignore, then connect it with git remote add origin <url> and push.

Mistake 2: Editing on GitHub and on my computer at the same time

Twice in the first few days, the history splits and joins back together:

*   2301e05 Merge branch 'main' of https://github.com/nnamdi-security/tech-blog
|\
| * ff6ec87 Update README.md
* | bbda3f6 Replace placeholder with actual domain name
|/

I had edited the README directly on GitHub's website, which created a commit there. Then, without pulling first, I made a commit on my computer. My local main and GitHub's main had each moved forward in different directions. When I ran git pull, Git joined them with an automatic merge commit. A few days later I did exactly the same thing with another file.

No work was lost, so it was not a disaster. But these merge commits clutter the history, and if both edits had touched the same lines, I would have had a merge conflict to resolve.

How to avoid it

Make git pull the first thing you do every time you sit down to work:

git pull origin main

If you have already committed locally and find that the remote has moved on, rebase instead of merging. Your local commits are replayed on top of the remote ones, giving you a straight-line history:

git pull --rebase origin main

You can make this the default so you never have to remember it:

git config --global pull.rebase true

Mistake 3: A folder name that did not match the URL

This one reached the live site. My variables tutorial lived in posts/variable-explained/. But this blog builds every post card and "next post" link from a metadata file, and that file said the post's URL was /posts/javascript-variables/. Every link to the new post went to a 404 page.

The fix was a single rename, and Git recorded it like this:

bug fix: navigation issue with the latest post-variable in javascript

 posts/{variable-explained => javascript-variables}/index.html | 0
 1 file changed, 0 insertions(+), 0 deletions(-)

Zero lines changed, but a broken site was fixed. Git spotted that this was a move, not a delete and a new file, because the contents were identical.

How to avoid it

  • Decide the slug first, and use it everywhere: the folder name, the URL, the canonical link, and the metadata.
  • Rename files with git mv old-name new-name, so the rename is staged in one step.
  • Before pushing, run the site locally and click every link to the new page.

Mistake 4: Committing everything straight to main

Every commit in this repository's early history went directly onto main. Because Netlify deploys automatically from main, every push went straight to the live site, including the broken link above.

How to avoid it

Do your work on a branch, and only merge it into main when it is ready:

git switch -c new-post-git-mistakes
# ...write, commit, and test...
git push -u origin new-post-git-mistakes

Then open a pull request on GitHub. Netlify can build a deploy preview for every pull request, a private copy of the site with your changes, so you can click around before anything goes live. Even when you work alone, a pull request gives you one last look at the full set of changes.

Mistake 5: Vague commit messages

Compare two messages from this repository:

  • Replace placeholder with actual domain name: clear, specific, and easy to find later.
  • bug fix: navigation issue with the latest post-variable in javascript: it says something was fixed, but not what the fix was.

A good commit message completes the sentence "If applied, this commit will…". For the rename above, that would be:

Rename variables post folder to match its URL slug

Six months from now, when you search the history for why something changed, you will be glad you wrote it that way.

My Git routine now

  • Start every session with git pull.
  • Create a branch for each post or fix.
  • Make small commits with messages that say what changed.
  • Use git status and git diff before every commit.
  • Open a pull request and check the deploy preview.
  • Merge into main only when everything works.

Key takeaways

Almost every beginner Git mistake comes from two copies of a repository drifting apart: your computer and GitHub, or main and the change you are working on. Pull before you start, work on branches, and let your commit messages explain your thinking. And do not be embarrassed by a messy history. Mine is public, and it taught me more than any tutorial did.
