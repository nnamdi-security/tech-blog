Web Security Basics for Front-End Beginners

Learn what XSS is, why innerHTML can be dangerous, and how HTTP security headers protect a static website, with examples from this blog's own code.

Nnamdi Ileh3 November 202610 min read
  • Security
  • JavaScript
  • Netlify

It is easy to assume security is a backend problem. This blog has no server, no database, and no login, so what could go wrong? Quite a lot, as it turns out. The browser runs your JavaScript, displays your content, and loads files from other websites, and each of those is a chance for something to go wrong.

This article covers three security basics every front-end developer should understand. I use real code from this blog as the example throughout.

1. Cross-site scripting (XSS)

Cross-site scripting, or XSS, happens when an attacker gets their own JavaScript to run on your page. Once it runs, it can do anything your own code can do: read what the user types, change the page, send data to another server, or act as the user on your site.

The most common cause is treating text as HTML. Imagine a search page that shows what the user searched for:

// ❌ Dangerous: the search term is treated as HTML
const query = new URLSearchParams(window.location.search).get("q");
results.innerHTML = `<p>Results for ${query}</p>`;

This works fine for a search like javascript. But the query comes from the URL, and anyone can write a URL. An attacker could send someone a link like this:

/posts/?q=<img src=x onerror="alert(document.cookie)">

The browser parses the query as HTML, tries to load an image that does not exist, and runs the onerror code. A real attacker would run something more harmful than an alert.

The fix: treat text as text

When you only need to display text, use textContent. The browser displays the value exactly as written and never interprets it as HTML:

// ✅ Safe: the search term is always displayed as text
const message = document.createElement("p");
message.textContent = `Results for ${query}`;
results.replaceChildren(message);

When you do need innerHTML, escape the data

Sometimes building an HTML string is the cleanest option. This blog builds every post card as a template string and inserts it with innerHTML. To keep that safe, every value goes through an escaping function first, which you can find in post-renderer.js:

function escapeAttribute(value) {
    return String(value)
        .replaceAll("&", "&amp;")
        .replaceAll('"', "&quot;")
        .replaceAll("<", "&lt;")
        .replaceAll(">", "&gt;");
}

// Every value is escaped before it touches the HTML string
`<h3><a href="${escapeAttribute(post.url)}">${escapeAttribute(post.title)}</a></h3>`

After escaping, <script> becomes &lt;script&gt;, which the browser displays as text instead of running as code.

Strictly speaking, the post data on this blog comes from a file I write myself, so it is trusted. But data has a habit of moving. If the posts ever come from a CMS, an API, or a guest author, the escaping is already in place. Escaping by default costs very little and saves you from having to remember later.

Ask one question about every innerHTML

"Could any part of this string ever come from someone other than me?" If the answer is yes, or even maybe, use textContent, escape the values, or sanitise the HTML with a well-tested library such as DOMPurify.

2. HTTP security headers

Every time a browser downloads a page, the server sends HTTP headers along with it. Some of these headers tell the browser to turn on extra protections. On Netlify you set them in netlify.toml, and this blog already sends four:

[[headers]]
  for = "/*"
  [headers.values]
    X-Content-Type-Options = "nosniff"
    Referrer-Policy = "strict-origin-when-cross-origin"
    X-Frame-Options = "SAMEORIGIN"
    Permissions-Policy = "camera=(), microphone=(), geolocation=()"

Here is what each one does.

X-Content-Type-Options: nosniff

Browsers sometimes "sniff" a file to guess its type when they are not sure what it is. An attacker can abuse this by uploading a file that looks like an image but contains JavaScript. nosniff tells the browser to trust the declared content type and never guess.

X-Frame-Options: SAMEORIGIN

This stops other websites from loading your pages inside an <iframe>. Without it, an attacker could load your site invisibly on top of their own page and trick people into clicking buttons they cannot see. This attack is called clickjacking. SAMEORIGIN allows only your own site to frame your pages.

Referrer-Policy: strict-origin-when-cross-origin

When someone clicks a link to another website, the browser normally tells that website which page they came from. Full URLs can contain private information, such as search terms or IDs. This policy sends the full URL only within your own site and sends just the domain name to other sites.

Permissions-Policy

This blog never needs the camera, microphone, or location. Turning those features off with an empty list, (), means no script on the page can ever ask for them, including scripts inside embedded content.

3. The next step: a Content Security Policy

The strongest browser defence against XSS is a Content Security Policy (CSP). A CSP is a header that lists exactly where your page is allowed to load scripts, styles, images, and frames from. If an attacker manages to inject a script, the browser refuses to run it because it is not on the list.

This blog is a good candidate for a strict CSP. Its only inline <script> tags are JSON-LD, which is data and is never run, and one small script on the 404 page, which you can allow by adding its hash ('sha256-…') to script-src. It has no inline style attributes. The only third-party content is the YouTube embeds. A policy for it could look like this:

[[headers]]
  for = "/*"
  [headers.values]
    Content-Security-Policy-Report-Only = """
      default-src 'self';
      script-src 'self';
      style-src 'self';
      img-src 'self' data:;
      frame-src https://www.youtube-nocookie.com;
      form-action 'self';
      frame-ancestors 'self';
      base-uri 'self';
      object-src 'none'
    """

Notice the header name: Content-Security-Policy-Report-Only. In report-only mode the browser does not block anything. It only logs violations in the developer console. That lets you browse the whole site, find anything the policy would break, and adjust it. Once the console stays clean, rename the header to Content-Security-Policy to start enforcing it.

A CSP does not replace escaping. It is a second line of defence for the day something slips through.

Bonus: a few habits worth building early

  • Never put secrets in front-end code. Anything in your HTML, CSS, or JavaScript can be read by anyone who opens the developer tools. API keys that must stay private belong on a server or in a serverless function.
  • Keep secrets out of Git. This blog's .gitignore excludes .env files for exactly this reason. A secret that has been pushed to a public repository should be treated as leaked, even if you delete it afterwards.
  • Protect forms from spam. The contact form uses a hidden honeypot field that people never fill in but bots do. Netlify quietly drops any submission that fills it in.
  • Prefer HTTPS everywhere. Netlify provides it automatically, but make sure every external link, image, and embed uses https:// too.

Security checklist for a static site

  • Untrusted text is displayed with textContent, not innerHTML.
  • Any HTML built from data escapes every value.
  • nosniff, X-Frame-Options, Referrer-Policy, and Permissions-Policy headers are set.
  • A Content Security Policy is tested in report-only mode, then enforced.
  • No secrets in front-end code or Git history.
  • Forms have spam protection.

Key takeaways

A static site is a much smaller target than a full web application, but it is not a zero-risk one. Treat text as text, escape any data you turn into HTML, and let HTTP headers ask the browser to protect your visitors. You can check your own site's headers for free at securityheaders.com.
